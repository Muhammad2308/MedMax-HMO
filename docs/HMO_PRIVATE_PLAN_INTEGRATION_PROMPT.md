# HMO Private Plan Integration — Backend Explanation Request

**Audience:** Backend/API implementer for the Laravel service at `C:\Users\DELL\Desktop\IX2 App\IX2 App\IX2 App`
**Priority:** Produce the explanation requested below before building anything. This is a reconciliation request, not an implementation ticket — the design already exists but predates the current multi-tenant architecture and was never checked against it.
**Trigger:** A freshly registered HMO (via the new commercial registration flow) has an empty "Health Scheme" dropdown in the enrollee-import UI, with no way to populate it itself. Investigating this surfaced a larger unresolved question about how private/informal plan management is meant to work.

## What's confirmed so far (frontend-side investigation)

1. **No self-service schema creation exists for an HMO.** The only HMO-facing schema route is `GET /hmo/schemas` (read-only, `ProviderController::schemas`, scoped correctly to `hmos.id = $request->user()->hmo_id`). Schema *creation* is `POST admin/org/schemas` on `MasterAdminOrgController`, under the `admin/org` route group gated to platform admins (`is_org_admin=true` AND no `hmo_id`/`provider_id`/`package_schema_id` — an HMO admin is structurally excluded from this gate). There is no path for an HMO to create or request a schema today.
2. **A private-plan design already exists but was never built.** `IX2_HMO_PRIVATE_PLAN_DESIGN.md` (backend repo root, dated 2026-06-26) specifies a complete `hmo_plans` system — category × subscription-type product grid, rider add-ons, per-provider negotiated pricing (`hmo_plan_providers`, `hmo_plan_provider_treatments/drugs/service_fees`), and an `enrollee_plans` many-to-many pivot — explicitly designed so **the HMO is its own plan authority with no `Schema` row required**. Verified in code: none of `hmo_plans`, `HmoPlan`, or any related table/model/controller exists. Only the old `packages`/`package_services`/`package_treatments`/`package_drugs`/`package_drug_prices`/`package_schemas` tables exist — the design doc itself documents these as half-built and structurally broken (no treatment FK on `package_treatments`, drug data stored inline instead of by FK on `package_drugs`, `package_schemas` has no FK to `packages` at all) and recommends dropping them after migration, not extending them.
3. **The private-plan design doc predates the MEDiX multi-tenant rebuild.** It has no mention of `hmo_deployments`, activation contexts, or the `/auth/hmo-registration/drafts/*` flow (draft → CAC verify → confirm → submit) that now provisions every new HMO. A freshly provisioned HMO today (`CommercialHmoRegistrationService::provisionWithinTransaction`) gets an `HMO` row, a `HmoDeployment`, an admin `User`, and nothing else — zero schemes, zero plans, zero providers on any panel.
